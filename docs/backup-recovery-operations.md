# Backup and recovery operations — Home and Research

The ordinary Backups page is available to a currently approved Home owner or
Research operator. Members and participants retain only their own authority.
App-only Home uses host operations; it has no Console page or service credentials.

## Read the observations separately

| Observation | Meaning | Next action |
| --- | --- | --- |
| Local downloadable backup | A completed collected artifact is available on this server | Retain matching recovery material; a download alone does not establish host-loss protection |
| Verified destination bytes | Full destination readback matched the selected opaque payload | Keep the independent key, committed kit, producer trust and settings export separately; run recovery qualification |
| Historical success with unknown state | The worker has not provided a recent valid heartbeat, or observation is invalid | Check the worker and explicit configuration; do not treat the old timestamp as current protection |
| Stale verification | Previously verified objects have not been successfully rechecked within the stated window | Inspect destination availability and worker operation; retain all previous objects and local obligations |
| Unavailable destination | Copy or verification failed | Restore access using the same bound destination and state, then restart the worker; uncertain work reconciles exact bytes |
| Degraded/full queue | Transfer backlog is old or capacity is approaching its bound; capture may be refused at exhaustion | Restore transfer or provision reviewed capacity; preserve obligations and previous usable downloads; later rescan cannot recover native results already rotated away |
| Missing recovery material | Copying may work while recovery selection is incomplete | Obtain the matching separately held material and run native preflight; do not substitute another kit or infer latest settings from timestamps |

The heartbeat becomes unknown after two minutes; verified readback becomes stale
after 26 hours, with normal remote revalidation after 24 hours. A successful copy
has no knowledge of every newest record, setting or erasure. Current schedules
and retention remain unchanged; transfer timings are observations, not guarantees.

## Recover without overwriting a target

1. Preserve the source if available, every selected input and all earlier attempts.
   Stop the source services for the drill; retain their volumes. Do not restore
   over an existing deployment or an existing staging directory.
2. Use the existing [read-only host fetch](../release/off-machine/README.md#host-recovery-retrieval)
   to stage exactly selected backup/evidence objects in a new private directory.
   The fetch credential is separate from the uploader's writer identity.
3. Supply an independently held committed kit, key, producer trust and genuine
   settings export. A newer independent evidence selection can exclude erasures
   made after an older backup; the selected evidence does not cover future erasures.
4. Run native recovery-set preflight and the [protected guided recovery](../release/guided-recovery/README.md).
   Review the bound inputs and fresh target before confirming. A browser retry
   must not replay uncertain restoration mutations.
5. After interruption, preserve the journal and partial target for inspection.
   Do not clear them to retry. Begin a separately approved attempt with a fresh
   target after reviewing the recorded stopping point.
6. Activate a completed recovered target explicitly using supported initialization;
   verify the selected Home mode, owner authentication, private-store isolation,
   erasure exclusion and Research study/consent. Collector enrollment is a separate
   explicit operator action. Cutover/deployment requires its own authorization.

Never give the uploader recovery keys, kits, human administrator credentials,
record stores or a Docker socket. Never repair a conflicting remote object by
silently replacing it. Keep remote deletion disabled and avoid bucket expiry.

## Acceptance boundaries

Real AWS qualification is deferred to the bottom of the backlog with pre-release
tests. Local TLS fixtures establish neither AWS permissions nor physical
independence. Separate-host recovery and custody require their own evidence.
No real destination, credentials or external transfer is authorized by this guide.
