# Reply to the Voptrack app team: common Track catalogue

Prepared for the owner, 5 November 2026. Not sent. Supersedes the earlier proposal
that the first household web authoring release would install catalogue types.
No common-track authoring or catalogue installer is currently implemented.

## Received and integrated, 6 November 2026

The app export is now vendored under `catalogue/1` and `catalogue/2`, with source
provenance in `catalogue/source.json`; this replaces the proposed path below.
Console embeds and verifies v2 and uses its declared read modes for qualified
existing types. It does not install or change types. See the
[catalogue documentation](../../catalogue/README.md) for
supported readers, validation and remaining gaps. The original requirements follow for reference.

## 1. Export and delivery

Please provide **one versioned bundle containing a manifest and one JSON document
per type**, generated by the same app installer code used for the release. Include
all ancestors/dependencies, and the exact app-installed Subject, Category and
required registration/reference schemas and records in the test vectors.

Preferred distribution: an immutable, versioned app release asset, with its
SHA-256 and app source revision. We will review and vendor a pinned copy under
`specs/app-catalogue/<catalogue-version>/` in this repository. That is the proposed
consumer path, not an existing integration. Console will use the shipped bundle;
it will not fetch a mutable branch or “latest” catalogue at runtime. A repo-path
export from the app team is also acceptable as the initial delivery if it identifies
an immutable source commit. Do not parse Swift to produce a second definition.

Manifest requirements:

- Format version, catalogue version, source revision and supported app/reader
  compatibility range; file paths, SHA-256 hashes and dependency order.
- Each entry's type ID and immutable declaration identity. Hash the exact exported
  document bytes; include a separate install-payload digest if the document also
  includes presentation data. Define precisely which payload bytes the digest covers.
- Exported installation payloads, with parent/ancestor identity, ordered own fields,
  field ownership (`meta_id`), types/scales, roles and annotations at every level.
- Presentation and metric declarations separate from the exact install payload
  where they are app-local: English labels, subject kinds, input constraints,
  canonical/display unit rules, money scale and currency field, spending flag,
  category/subject references, default metrics and period policies.

Please distinguish the **declared installation payload** from the **effective
inherited metadata** returned by a store. We need vectors for both. A digest of a
GET response is not automatically the digest of the original catalogue payload.
Agree the comparison procedure, preserving field order, ancestor identities and
annotation JSON values without losing precision or rewriting opaque annotation
content. No server-invented annotation key will be added to carry provenance.

## 2. First-release boundary and version policy

**First household web authoring release: only record to types the app has already
installed. No web Track creation, schema installation, parent creation, annotation
updates or hidden app-internal registration/preferences writes.** The existing
review demo is still read-only; this is the boundary for the next authoring slice,
not a claim that record editing already ships.

That recording scope is limited to the explicitly discovered common household
dataset. Member datasets remain read-only in the web, including an owning member's
one-way copies. Absence of a readable `home_copy` marker is never permission to
write. Read-only members see history; every mutation uses the person's current
read/write authority, without owner, custodian or Home-service credential fallback.

Before enabling an input form or specialized reduction, verify the installed
full declaration and dependencies against a supported pinned catalogue entry.
The type ID alone is insufficient. An unknown, legacy or mismatched declaration
stays available as permission-bound raw history, with an explicit unsupported-type
state; disable unqualified forms and reductions rather than silently guessing.
The legacy dashboard adapters are not that compatibility check.

Accept the proposed immutable-type policy: **no schema mutation within a catalogue
major, and no schema mutation merely because a new major exists either.** A changed
declaration requires a new type ID and compatible ancestor/dependency IDs. Upgrading
the server's bundled catalogue must not redeclare types already present in a store.
Two app releases may share a catalogue identity only if their expectations agree.
A provenance/version receipt must be bound to the qualified dataset/type identity
and payload hash. Please export the approved receipt/version representation or
include the agreed provenance in the app-generated declaration before installation.
We will not retrofit annotations onto frozen types or infer their version from names.

A later web installer would be a separate slice: use only exact exported payloads,
read/compare an existing declaration and ancestors in full, and handle concurrent
create conflicts by reading back and accepting only an exact match. A preflight
GET is not a lock. Mismatches fail visibly; no alternate type, automatic merge,
annotation repair or parent modification. We must qualify this through supported
Tessera interfaces and shared race vectors before enabling installation.

## 3. What is missing in Console today

The findings below describe the earlier Tessera v0.1.0-rc.2 integration.

- **Opaque annotation reading is now implemented locally.** The Home reading slice
  retains JSON numbers without losing precision, plus booleans, objects, arrays,
  null and strings. Existing string `meaning`/unit adapters remain partial semantic
  support. We still need app-generated vectors to qualify how exported values are used.
- **The current metadata projection is not an install verifier.** Field `meta_id`
  and immutability are now retained, but effective-schema comparison is not a
  byte/hash comparison against the complete app payload and ancestor catalogue.
- **App-local semantics need an export.** `TrackAnnotation.swift` deliberately keeps
  symbols, colors, input hints and chart preferences app-local. Default metrics,
  period rules, spending and money scale are not completely understood by Console.
  Export their actual declarations; schema field IDs are not enough to recreate them.
- **References need shared dependencies.** Category and Subject must be qualified
  objects in the same common dataset, never plain-text replacements. Readers need
  explicit authority for required metadata as well as records. We will not silently
  broaden existing member shares to expose private subject/source metadata.
- **Units and erasure need vectors.** Store the app's canonical values and recorded
  units; display conversion never changes stored values. Subject/Track deletion is
  deferred until its complete reference/metadata removal and recovery behavior is
  agreed and tested. No lossy conversion or partial “delete succeeded” state.

We have not identified a Tessera storage blocker for opaque catalogue annotations
or ordinary typed records from this investigation. The issues above are local
Voptrack consumer/contract work, not reasons to request a large upstream change.
Common-dataset grants, discovery and erasure guarantees remain separately
unqualified; their minimum requests and local alternatives are tracked in
[the dependency ledger](../tessera-dependencies.md#common-household-tracks).

## Shared acceptance vectors

Please include app-installed stores plus app-written records for every supported
catalogue type: schema/ancestor mismatch, unknown annotation JSON, old/new catalogue
compatibility, same ID with different hash, concurrent installation (later installer),
exact money/currency, canonical units, period boundaries, weighted aggregates,
latest/reset identity, missing member versus real zero, qualified Subject/Category,
metadata access denied, copied history updates/deletions and read-only mutation
refusal. Include catalogue provenance and complete subject/Track erasure examples.
Tessera's own specs and vectors remain the protocol authority.
